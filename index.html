Do we need our own engine?

Inkling 2 Mini in llama.cpp on a base Apple M5: every change that took it from 15.9 to 28.4 tokens/s, what did not work, and how close it gets to the hardware.

By Koosh0610 · November 2026 · Code: Koosh0610/llama.cpp-inkling

Short version

  • Upstream llama.cpp has no Metal kernels for NVFP4, the format Inkling 2 Mini's experts ship in, so on a Mac the experts ran on the CPU: 42.8 tokens/s prefill and 15.9 tokens/s decode on a base M5.
  • Native NVFP4 kernels moved the experts to the GPU (251 / 24.2). After that, decode time tracked the number of memory-barrier levels per token, about 1.5 µs each, not the number of kernel launches.
  • Fusions written for this model and a wider graph reorder cut barrier levels per token from 3,257 to 1,783. Final result: 362 tokens/s prefill and 28.4 tokens/s decode, 78% of what the memory bandwidth allows, with the same output quality as upstream.
  • All of it fit inside llama.cpp's existing structure. We did not need our own engine.

1. The question

We kept hearing that llama.cpp had fallen behind in 2026, and that anyone serious about local inference on a Mac should use MLX or write an engine for their model. We had a concrete case to test that on: Inkling 2 Mini on a base M5 MacBook with 24 GB.

Out of the box the gap was real. Upstream llama.cpp decoded 15.9 tokens/s and processed a 512-token prompt at 42.8 tokens/s. MLX on the same machine did 27.2–27.7 and 411–421.

The repo keeps the probes we wrote while weighing a custom engine: a bandwidth test, mat-vec layout prototypes, a persistent-kernel experiment. But when we looked at where llama.cpp spent its time, almost all of it could be fixed in place. This post goes through every change with what it measured; the appendix lists them in build order.

In a side-by-side llama-server test on the same model file, upstream decoded 16.9–17.8 tokens/s and this repo 28.8–29.0.

The repo is a fork of llama.cpp at 46eb174. Each change is one commit with its measurement in the message, so git log --reverse reads as the story; the commit links below point there, and the tag m5-benchmarked-build is the exact tree we benchmarked.

2. Model, Mac, baseline

The model

Inkling 2 Mini is a mixture-of-experts model with 24 layers of weights whose middle layers loop: layers 6 to 17 run three times, so every token makes 48 layer visits (Figure 2). Each visit routes the token to 8 of 128 experts. The hidden state is 2,304 wide.

Three things about it matter for speed:

  • The loop adds reads, not weights. The 12 core layers are streamed from memory three times per token.
  • A lot of small vector work. There is no RoPE: positions come from a relative-position bias with attention sinks. Q, K and the relative-position queries are clipped to a maximum L2 norm. K, V, the attention output and the MoE output each pass through a short causal convolution that keeps state. Instead of a plain residual add, a depth mix attends over earlier block outputs with learned queries. In passes 2 and 3, loop controllers (a rank-64 projection followed by two tanh-gated mat-vecs) mix a message from the previous pass into each layer's inputs.
  • New number formats. The experts ship in NVFP4 (layers 0–19) and MXFP8 (layers 20–23).

We ran Unsloth's UD-Q3_K_XL GGUF (13.6 GB). It keeps most experts in NVFP4 as released but cuts 8 of the 40 NVFP4 expert tensors to 2–3.4 bits and the MXFP8 layers to 3–4.5 bits. Attention is Q8_0 and the output head is Q5_K (318 MB).

The Mac

A base M5 MacBook: 10-core GPU and 24 GB of unified memory, which the CPU and GPU share. The nominal memory bandwidth is 153 GB/s; the best streaming read we measured from a Metal kernel was about 125 GB/s. That number sets the ceiling for decode, because every token has to read every active weight once.

The baseline

Upstream llama.cpp at 46eb174, plus one fix. Without upstream PR #32704 (merged a few hours after 46eb174), the copies of the core layers used by passes 2 and 3 are made before the per-expert scale tensors are attached, so those passes run the NVFP4 experts unscaled and the model outputs gibberish (perplexity about 67 instead of 4.4). The fix re-shares the loop slots after the scale pass (0f29f91). Every number in this post includes it.

With it, upstream measured 42.8 tokens/s prefill (pp512) and 15.9 tokens/s decode (tg128) with flash attention. The cause is one line in ggml's Metal backend: ggml_metal_supports_mul_mat_op returned false for NVFP4. The scheduler therefore ran the NVFP4 expert mat-vecs on the CPU, and the graph bounced between the GPU and CPU backends in every layer.

3. How we measured

Tools first, because the first tool we trusted pointed us the wrong way.

  • Speed: llama-bench pp512 and tg128 with flash attention. Run-to-run noise was about ±0.6 tokens/s, so anything under about 2% was checked with an interleaved A/B in the same time window: the two builds alternate, eight rounds each.
  • Power state: on battery, Low Power Mode off. Low Power Mode cut bandwidth to about 80 GB/s and invalidated an hour of results before we noticed; after that we checked it before every run.
  • Quality: dcheck, a greedy decoder that saves the logits of every step and compares them with a reference (largest logit difference, mean KL divergence, first top-1 divergence) on three prompts, plus perplexity and KL divergence against upstream at milestones.

The profiler

We added a GPU timestamp profiler (48a4afd): the whole graph goes into one command buffer, with one compute encoder per fusion group and GPU timestamps at each encoder's start and end. A command buffer is the unit of work the CPU submits to the GPU; an encoder records the kernel dispatches inside it. Figure 3 is one decode token at full power, right after the NVFP4 kernels landed.

The largest bucket was not a weight read. Figure 4 shows where those small ops live: between every pair of weight reads in a layer visit there is a stretch of tiny kernels on 2,304-wide vectors (norms, clips, convolutions, the depth mix, the controllers). Multiply that by 48 visits and the decode graph has more than 5,000 nodes.

Why the profiler misled us

Our first plan followed the profile: fuse small ops to cut dispatches. The first fusion removed about 1,000 dispatches per token and gained 4%. The loop-controller fusion replaced eight ops per controller and gained 0.8%. Removing 199 CONT ops that ran concurrently with other work gained nothing. The profile had also shown one IQ2 expert kernel at 707 µs, which turned out to be the GPU clock ramping up inside the profiler.

The method was the problem. In profile mode each fusion group gets its own serial encoder, so nothing overlaps, and every group pays an encoder switch and a clock ramp. Small ops look far more expensive than they are in the real graph, where they run next to other work. The profiler's commit message says as much; we learned it the slow way.

What did predict cost: barrier levels

A Metal compute encoder can run in concurrent mode: its dispatches may overlap unless a memory barrier separates them. ggml-metal uses that mode and inserts a barrier only when an op reads or writes memory that an op in the current concurrent group writes, or writes memory that group reads. The upstream encoder loop:

bool is_concurrent = ggml_metal_op_concurrency_check(ctx, node);
...
if (!is_concurrent) {
    ggml_metal_op_concurrency_reset(ctx);  // memoryBarrierWithScope, clear the ranges
}

So a graph runs as a sequence of levels: a group of independent dispatches, a barrier, the next group. At every barrier the GPU drains (the slowest kernel of the level finishes) and then the next level's kernels ramp up again (Figure 5).

Two measurements pinned this down. The GPU was busy for about 35.0 of the 35.6 ms of a token, so CPU-side launch overhead was not the limit. And the time saved tracked the levels removed, at about 1.5 µs per level: a dispatch that joins an existing level costs almost nothing, an op that depends on the previous one adds a level. A bare dispatch plus barrier costs about 0.7 µs in a microbenchmark; in the real graph, removing a level saved about 1.5 µs, the difference being kernel ramp-up and tail. From then on our main metric was barrier levels per decode token.

4. NVFP4 kernels on the GPU

NVFP4 stores 64 weights in 36 bytes: four one-byte UE4M3 scales, one per 16 weights, and 32 bytes of 4-bit E2M1 codes (Figure 6). We added the four kernels the scheduler needs (54ce6c4): mul_mv (mat-vec), mul_mv_id (the MoE mat-vec, which picks expert matrices by id), and mul_mm and mul_mm_id (mat-mat, for prompt processing).

The mat-vec does the decode work. A simdgroup is 32 GPU lanes that execute in lockstep. Each lane takes whole 32-weight halves of 64-weight blocks, for two rows at a time, with four simdgroups per threadgroup. A 2,304-wide row is 72 such halves per simdgroup, and the second row keeps more independent loads in flight.

Decoding the codes needs no lookup table. Put an E2M1 code's three magnitude bits into an fp16 bit pattern at bit 9 and its sign at bit 15, and the result is exactly the fp4 value times 2−14: E2M1's exponent bias is 1 and fp16's is 15, and E2M1's one subnormal value (0.5) lands on an fp16 subnormal. Upstream's MXFP4 mat-vec already decodes this way; its comment notes that it is the same decode as MLX's. The scale byte works the same way: shifted left by 7, a UE4M3 byte is an fp16 number equal to the scale divided by 256. The kernel multiplies each row's sum by 222 once at the end.

Results: test-backend-ops NVFP4 MUL_MAT passes 125/125. Prefill went from 42.8 to 251 tokens/s and decode from 15.9 to 24.2, with perplexity 4.412 against upstream's 4.423, KL divergence 0.0019, and the same top token 98.8% of the time.

One piece came later (51bac5a). The mat-mat path dequantizes tiles through dequantize_nvfp4, which still used a 16-entry table. At 512 tokens the NVFP4 MoE mat-mat ran at 5.7 TFLOPS against 6.9 for Q4_0, limited by dequantization. Switching it to the bit placement, four codes at a time:

// e2m1 nibbles placed at fp16 bit 9 (magnitude) and bit 15 (sign) are the fp4 values times 2^-14, exactly
static inline float4 e2m1x4_to_f32(uint w, float d) {
    const ushort4 n = ushort4(as_type<uchar4>(w));
    return float4(as_type<half4>(ushort4(((n & 7) << 9) | ((n & 8) << 12))))*d;
}

made the 512-token MoE matmuls faster (gate_up 7.58 → 5.96 ms, down 3.81 → 3.09 ms, 7.0–7.3 TFLOPS, now above Q4_0) and took prefill from 330 to 343 tokens/s, bit-identical.

A grouped MoE kernel for small batches

Speculative decoding verifies a few tokens at once. The standard MoE mat-vec handles each (token, expert slot) pair on its own, so if two tokens pick the same expert, its weights are read twice. The grouped kernel (7aca306), used for 2 to 8 tokens and at most 64 pairs, has each lane of a simdgroup load the expert ids of two pairs. A SIMD ballot then gives a 64-bit mask of the pairs that chose this threadgroup's expert; the lowest set bit is the owner. The owner decodes the weights once and computes every pair that uses them, and the other pairs exit (Figure 7).

It is correct, a small gain at 8 tokens and about neutral at 4. Tokens rarely share experts, so there is little to deduplicate. That fact comes back in the speculative decoding section.

5. Fusing the stretches between weight reads

The idea came from Locals, a local inference server that runs Inkling 2 Mini with its own kernels; its runtime notes describe making each stretch between two weight reads one kernel. ggml-metal already has the machinery for that: a fusion table where each entry is an op sequence plus a check function, and an encoder that emits one kernel for a matched run of graph nodes. Our patterns change shape inside the chain (row reductions, permutes), so each check runs ggml's structural subgraph test itself: no intermediate result may be read outside the chain.

Before fusing, we bounded the gain with switches that skip whole blocks (0b823b1; the output is wrong, the timing is not): the short convolutions cost about 2.0 ms per token and the depth mix 1.3–2.0 ms.

L2_CLIP

The model clips each row of q, k and the relative-position queries r to an L2 norm of at most a threshold. In the model code (inkling2.cpp) that is a few lines:

if (scale) {
    cur = ggml_mul(ctx0, cur, scale);
}

ggml_tensor * norm = ggml_sqrt(ctx0, ggml_sum_rows(ctx0, ggml_sqr(ctx0, cur)));
norm = ggml_scale_bias(ctx0, norm, 1.0f, 1e-6f);

ggml_tensor * factor = ggml_div(ctx0, ggml_fill(ctx0, norm, threshold), norm);

return ggml_mul(ctx0, cur, ggml_clamp(ctx0, factor, 0.0f, 1.0f));

On the GPU that is nine dependent kernels, so nine barrier levels, three times per layer visit (Figure 8). kernel_l2_clip_f32 (659aa87) does it with one simdgroup per row: about 1,000 fewer dispatches per token, decode 24.17 → 25.13 tokens/s, prefill 251 → 263, KL divergence against upstream 0.0018.

SITU

The MoE activation is a softcapped gate, b·tanh(g/b)·sigmoid(g) · lb·tanh(u/lb): nine ops between the gate_up and down expert reads. One kernel (48bd597): decode 25.56, prefill 280, KL divergence 0.0017.

LOOP_CTRL

In passes 2 and 3 each controller computes cur − tanh(Wfx)·cur + tanh(Wgx)·msg: two small mat-vecs and six elementwise ops, now one kernel with a simdgroup per output channel, for up to 8 tokens (f32b088). It gained only 0.8%. Outputs were identical on three of four prompts; the fourth diverged at a near-tie. This was the result that made us doubt that dispatch count was the cost.

F16 router and controller weights

Not a fusion. The router (a 2,304 × 128 matrix per layer) and the controller weights ship as F32, about 283 MB read per token. We added LLAMA_QUANT_ONLY_MATCHED (c653231), which makes llama-quantize change only the tensors that a --tensor-type pattern matches, and converted those 168 tensors to F16 with this pattern file (f91b658):

ffn_gate_inp\.weight=f16
loop_.*_ctrl_.*\.weight=f16

Decode +3.4%, KL divergence unchanged. That file is the one we used from then on.

Identity ops

For a single token, the depth-mix query repeat and the expert-scale repeat were plain copies, and the zero attention sinks were rebuilt in every layer. Skipping the repeats and sharing one zero-sinks tensor per graph (4457fc3) left decode about unchanged and added 3% to prefill.

CONV_RES

The short convolutions end in SSM_CONV, ADD, SCALE. The convolution output reaches the ADD through a RESHAPE view, so this matcher checks the raw node span, views included (fa85426). The conv state copy is emitted earlier by the graph builder and stays outside the pattern. Decode +2.2% (26.4 → 27.0), identical outputs.

6. Letting the reorder see further

Before encoding, ggml-metal reorders the graph to fill each concurrent group. When a node conflicts with the current group, it looks up to 64 nodes ahead for independent nodes that can join first. The look-ahead stops at the first op that is not on a whitelist, and Inkling's graph is full of ops that were not on it. The whole change (e3c63bc):

case GGML_OP_CONCAT:
case GGML_OP_SOFT_MAX:
case GGML_OP_FILL:
case GGML_OP_PAD:
case GGML_OP_SQR:
case GGML_OP_SQRT:
case GGML_OP_LOG:
case GGML_OP_FLASH_ATTN_EXT:
    return true;

Barrier levels per token went from 3,257 to 2,656 and decode from 27.6 to 28.4 tokens/s, with bit-identical logits.

7. The depth mix

The depth mix replaces the residual add. It RMS-normalizes the earlier block outputs and the current state, scores them against a learned query, and returns the softmax-weighted sum. A decode token runs 120 of them: one before attention in every visit except layer 0's (47), one before the MoE in every visit (48), one per visit in passes 2 and 3 to build the messages (24), and one before the output head.

Many mixes in a graph read the same list of earlier blocks, so the first change caches the normalized stack and its transpose per distinct block list (151e465); each mix then normalizes only the current state. On its own that saved about 180 dispatches and no measurable time, but it reduced every mix to the same short sequence: an RMS norm, two concats with the cached stack, the score matmul, a softmax, and the weighted sum.

kernel_mix_f32 runs that sequence in one 1,024-thread threadgroup per query (7ff2d42). Barrier levels went from 2,656 to 2,213 and decode gained 2.1% in a same-window A/B, with mean KL divergence against the unfused build of at most 8e-5 and no top-1 change in 384 tokens.

Prefill had its own version of the problem: the skip switch put the mix at about 16% of prompt-processing time. Using the cached prefix at any batch size (be29e28, +8.4%) and running the fused kernel over a (query, token) grid with 256 threads per threadgroup (35c0667, +5.8%) took pp512 from 288 to 330 tokens/s. KL divergence against upstream moved from 0.00171 to 0.00180, about one standard error; perplexity 4.414, top-1 agreement 98.6%.

8. The last stretches

By the last day, the remaining levels sat in two places: the tail of each layer (a convolution, its state store and the residual adds) and the relative-position bias.

Two graph changes came first. The builder emitted nodes in an order that interleaved those patterns with unrelated work, so we emit the sink projection before the bias ops and each layer's output right after its conv state store (85c9b12, node order only). And build_attn cast the attention mask to F32 in every layer, 48 times per token; now the cast happens once per graph (ad73b19).

CONV_TAIL (b1f549c) fuses the concat with the conv history, the conv state copy, SSM_CONV, the residual ADD, SCALE and the optional second residual ADD into one kernel, at both the attention-output and the MoE tails, for one token. REL_BIAS (bbff17b) fuses the bias-table matmul, the sink subtraction, the permute and gather by distance, the mask add and the F16 cast, and writes the result straight into the flash-attention mask (Figure 9).

Together with the two graph changes: barrier levels 2,131 → 1,783 per token, decode 28.0 → 28.4 in an interleaved A/B (within noise), prefill 343 → 362. dcheck on three prompts showed no top-1 divergence over 128 tokens and mean KL divergence of at most 2.7e-4, the same as with the fusions off. We did not rerun perplexity for these two.

The gotcha: garbage from the first token

Fusing deletes intermediate tensors, and the graph allocator does not know that. It plans memory from the unfused graph, so if a fused kernel reads an input whose last use, as far as the allocator can tell, was an early node of the pattern, that memory can be handed to another tensor before the fused kernel runs. ggml handles this with alloc deps: the backend lists tensors to keep alive until a pattern's last node, and the scheduler inserts VIEW nodes after that node to hold them.

Upstream registered deps only for the longest pattern that matched at a node, but which pattern actually fuses is decided later, at encode time. We changed that to register the deps of every match, nested ones included, since extra deps only extend lifetimes (f59b466). Then CONV_TAIL arrived and its deps broke the allocation of the patterns nested inside it (MOE_REDUCE and CONV_RES): the model produced garbage from the first token.

The fix was to show that CONV_TAIL needs no deps at all. Each thread reads its own channel of every input and then writes that channel of the output, so even if the allocator places the output on top of an input, no thread can read a value another thread has already overwritten:

// conv_tail needs none: every graph input is read per channel by the thread that writes that channel, so an
// output placed over an input cannot race (its deps also broke the allocation of the nested patterns)
if (fusion->id == GGML_METAL_FUSION_CONV_TAIL) {
    return;
}

REL_BIAS keeps deps, but only on intermediates computed by the graph; weights, inputs and caches are never reused by the allocator. A 15-op variant that also folded the MoE expert sum into CONV_TAIL was dropped: it is longer than the 16-node limit for one fused run, and it is not alias-safe.

10. What did not work

  • Graph capture. Recording the command stream once and replaying it saves CPU encoding time. The GPU was already busy 35.0 of 35.6 ms per token, so the most capture could recover was about 0.6 ms. Not worth it.
  • A persistent megakernel. One long-running kernel per layer, with threadgroups syncing through a counter in device memory instead of barriers. Our probes (inkling-engine/mega/sync.mm) found the counter sync itself reliable up to 30,720 co-resident threads, and a persistent mat-vec kept full bandwidth. But plain stores from one threadgroup were not reliably visible to other threadgroups within the same dispatch: stale reads in 1–8 of 300 trials on a quiet GPU and up to 20 of 20 when another process used it, all silent. Metal's atomics are relaxed-only, so there is nothing to order the data behind the counter. The gain would have been at most about 0.3 µs per level anyway, against about 1.5 µs for removing the level by fusion.
  • Caching the looped weights. Passes 2 and 3 read the same 12 layers again, so why not keep them on chip? One pass reads about 780 MB, and the on-chip caches hold tens of megabytes. Only batching, which speculative decoding provides, amortizes those reads.
  • More command buffers. llama.cpp encodes a small first command buffer on the calling thread while helper threads encode the rest. A smaller first buffer and more encoder threads were both worse.
  • A longer reorder look-ahead. 128 or 256 nodes instead of 64: neutral or worse.
  • Fusing the controllers' down projection: neutral.
  • Lower-bit attention. Requantizing attention from Q8_0 to Q6_K gave +4% decode, but KL divergence against upstream went from 0.0017 to 0.0029. Our rule from the start was that no change trades away quality, so it was dropped.

11. Speculative decoding

Speculative decoding drafts several tokens cheaply and checks them in one forward pass of the full model. On a dense model, verifying a few tokens costs about as much as decoding one, because the weights are read once. On a MoE model each token picks its own 8 experts, and tokens rarely share them, so verifying more tokens reads more expert weights (Figure 11, top): 33.9 ms for one token, 52.5 for two, 117 for eight. From two tokens on, each extra token adds about 0.32 of a plain decode step.

DSpark (PR #32218 by Piotr Wilkin, fc9388d here) adds a block drafter for Inkling 2 that proposes up to 7 tokens per pass. Its Markov head conditions each drafted token on the previous one, and each of those 7 steps multiplies by the target model's full output head: a 318 MB read per step, 2.2 GB for all seven. A drafter pass took 29 ms, against 33.9 ms for a plain token. We made two changes:

  • A Markov-step cap (4b7c0dc). The drafter ran all 7 steps no matter how many drafts the caller would read. LLAMA_DSPARK_MARKOV_STEPS stops the chain early and passes the batched logits through for the rest; drafts are identical. With 3 steps a drafter pass takes 17.6 ms. Measured early, before the decode work, DSpark with 2 drafts and the cap ran 24.6 tokens/s against 23.84 plain (+3%), and +27% on a code prompt. Once plain decode got about 20% faster, the same setting lost on prose (21–22.5 against 29.0 tokens/s).
  • A gate (c757228), following the design in Locals' notes. Drafting stops at the first token the drafter gives less than 0.8 probability. That threshold (--spec-draft-p-min) did not work for Inkling 2 before: the old check read the drafter's context features where it expected confidence values, and stopped at once. It now uses the softmax probability of the drafted token, computed on the host. After tries that lose time, drafting pauses for 32 tokens, doubling up to 256, and a winning try resets the pause length to 32 (Figure 11, bottom). Empty drafts count as losses.

The gate scores each try in plain decode steps: tokens accepted minus an estimated cost of 0.85 steps for the drafter pass, 0.24 for the verify, and 0.32 per drafted token.

const float gain = n_accepted - (draft_cost + verify_cost + token_cost * last_len[seq_id]);
...
credit[seq_id] = std::min(credit[seq_id] + gain, 2.0f);
if (gain > 0.0f) {
    backoff[seq_id] = 32;
}
if (credit[seq_id] < 0.0f) {
    skip_left[seq_id] = backoff[seq_id];
    backoff[seq_id]   = std::min(backoff[seq_id] * 2, 256);
    credit[seq_id]    = 0.0f;
}

The results, on llama-server at temperature 0. Prose is three short prompts, code is one function-writing prompt (both up to 256 tokens), and copy is rewriting a 144-line Python file with one function renamed (thinking off, up to 1,600 tokens). Tokens/s:

What we take from it:

  • n-gram drafts need no draft model, lost nothing on prose or code in these runs, and give 3.2× on copy. They are the right default.
  • Gated DSpark on top adds 9% on copy (85.1 against 78.0, 3.5× plain) and 1.5% on code, and costs about 6% on prose: the drafter's per-token context update runs even while drafting is paused. Locals reports a similar cost for its own drafter on prose, about 4%.
  • The gate turns ungated DSpark's halving of prose speed into a loss of a few percent, and keeps its copy gain.
  • Code and copy outputs are identical to plain decoding. Two of the three prose replies flip at a near-tie in the reasoning under batched verify.
  • The lever left: each Markov step re-reads the whole 318 MB head. Biasing only the base model's top-K rows would make wide drafts nearly free.

13. How close to the limit

Decode reads every active weight once per token. For this file that is about 3.45 GB: 48 layer visits of attention, router and 8 experts, plus the output head. At the 125 GB/s we measured, reading it takes 27.6 ms, a ceiling of about 36 tokens/s. At 28.4 tokens/s we are at 78% of it (Figure 12).

Where the other 7.6 ms go is partly an estimate. If each of the 1,783 remaining barrier levels costs what removed levels saved, that is about 2.7 ms. That is about 37 levels per visit, mostly in the depth-mix and loop-control prologue. The remaining 4.9 ms we have not broken down. Known candidates: the NVFP4 ffn_down mat-vec runs at about 84% of bandwidth (worth about 0.5 ms), and the expert tensors that are not NVFP4 (IQ2_S, IQ3_XXS, IQ3_S, Q3_K, IQ4_NL) still run on upstream's kernels for those types; faster ones are an open item we estimate at about 1 ms. The output head already streams at 129 GB/s.

14. Caveats

  • One machine and one quant. Benchmark noise is about ±0.6 tokens/s. Everything was measured on battery with Low Power Mode off.
  • The quality numbers compare this engine with upstream on the same file. They do not measure what the quant itself loses against the released weights: UD-Q3_K_XL cuts 8 of the 40 NVFP4 expert tensors to 2–3.4 bits. UD-Q4_K_XL (17.6 GB) keeps them all but needs a raised GPU memory limit on a 24 GB Mac.
  • Perplexity was not rerun after the last two fusions; dcheck was.
  • MLX was measured once, with a different quant.
  • Nothing here is upstream yet. Debug switches (GGML_METAL_PROFILE, GGML_METAL_GRAPH_DUMP, INK_SKIP_*) are still in the tree, and the Markov-step cap is an environment variable where a proper fix would pass the draft count through.
  • CPU-only mode is broken upstream for this model (perplexity about 140,000), a separate bug we did not touch.

15. So, should you write your own engine?

For this model on this Mac, no.

The two big wins fit llama.cpp's existing structure. The NVFP4 kernels slot into the Metal kernel tables next to MXFP4. Each fusion is an entry in ggml-metal's fusion table plus one kernel. The reorder change is eight case labels, and the graph changes are a few lines in the model file. In all, 36 commits, each small enough to review on its own.

The things a custom engine would have let us try beyond that did not pay: a persistent megakernel is unsafe on Metal's relaxed-only atomics, graph capture is worth at most 0.6 ms, and the looped weights do not fit on chip.

What is left is mostly hardware and structure: about 125 GB/s of streaming bandwidth, a model that re-reads about 780 MB per loop pass, and a MoE whose verify cost grows with every token. We are at 78% of the bandwidth ceiling. The next gains are more fusion in the mix and controller prologue and faster kernels for the remaining expert types, not a rewrite.

What llama.cpp did need was a kernel for a format it had not seen, a reorder whitelist that was too cautious for an unusual graph, and fusions for chains that only this model has. Those are contributions, and the NVFP4 kernels are the first we would send upstream.
